Consolidated judgment

Four focused changes. No framework expansion.

  1. One active dialog lifetime. Replace the parallel dialog/completion lists and restore unfinished input when closing is abandoned, including failures.
  2. One accepted selection decision. Let the presentation owner decide selection and inspector transitions; remove the window’s second accepted-selection copy.
  3. One committed torrent-edit implementation. Merge and replacement keep their input rules, then share persistence and application of intended fields.
  4. A concrete speed-history owner. Put its buffers, aggregation and retention together, with samples supplied by the engine.

What changes from the first report: selection ownership is now recommended; speed history is a justified small extraction; tracker consolidation is defined around the committed edit, rather than a vague shared tracker module. Dialog recovery includes unsuccessful close paths.

The test is the code a maintainer must read: fewer independently mutable facts, fewer places deciding the same operation, and less navigation between preparation, execution and completion. A refactor can earn its place without a reproduced bug.

Suitable architecture for this product

Concrete owners, direct calls

WinUI process

  • MainWindow: native dialog lifetime, pickers, control gestures, focus and chrome.
  • MainViewModel: accepted product selection, command availability and transition decisions.
  • Draft owners / Inspector: unfinished choices, target identity, detail context and local submission state.
  • PipeClient: framing, correlation, connection outcomes and command/read scheduling.
  • TableView: reusable control selection, geometry and gestures.

Native engine process

  • Engine: accepted commands, torrent membership and operations.
  • Committed edit: one internal implementation for saving and applying intended torrent fields.
  • Changes: ordered saved-document changes.
  • Store: blocking work, atomic file replacement and completion delivery.
  • History: bounded samples and aggregation; libtorrent continues to own transfers.

These are responsibilities, not a mandate for one new class per row. The dialog lifetime can stay private to the window; the committed edit stays private to the engine. Move code or introduce a concrete type when it makes the operation easier to understand. Existing folders and partial classes have no special protection.

The two-process arrangement earns its cost through continued transfers when WinUI closes and isolation from a UI crash. One pipe, one engine state thread and complete snapshots remain proportionate. There is no demonstrated simplification from replacing them.

Chosen arrangement. Represent the active interaction once in MainWindow. Bind the dialog to its completion and, for draft-bearing interactions, its resumption behavior. Close suspends this interaction, obtains the existing discard decision, and either closes or restores the still-valid unfinished interaction.

Completion has a real meaning. Do not complete the lifetime merely because ShowAsync returned. Required command settlement, visual detachment, event cleanup and modal ownership release must finish first. Suspending for Exit must preserve drafts; ordinary cancellation keeps its existing meaning. Remove remains a confirmation, not an invented draft.

Source-supported recovery gap: CloseWindow hides editors before later awaits, but restoration currently depends on keepDraft, set only after CancelClose succeeds. An exception can leave the window alive with its unfinished editor hidden. Capture the suspended interaction independently of a successful protocol reply, and restore it when closing is abandoned and the draft is still valid. This path has not been reproduced at runtime.

Delete: the four completion fields, the repeated close-time enumeration, the restoration booleans, repeated deferred-Add conditions, and the parallel list used only for common theme/flow updates. Replace empty-target-plus-initialize-false resumption calls with the retained interaction’s resumption. Keep control references where specialized content actually needs them.

Do not add: a modal queue, dialog registry, public dialog interface, generic draft hierarchy or callback collection for every possible lifecycle event. A small private lifetime value and ordinary window methods are sufficient.

Payoff: locality for close/recovery decisions; leverage across four callers; greater depth because callers supply form behavior rather than reconstructing lifecycle rules.

Chosen arrangement. Keep merge and replacement as distinct entry paths. Resolve and validate their intended fields in ordered execution, then hand them to one private engine implementation that saves and applies the edit. Use a small concrete edit value only if it cleanly expresses fields that are present or absent.

The shared implementation derives desired facts from current accepted state, saves once when necessary, applies changed fields and completes the reply at the correct point. Saved equality may skip the disk write; it must not skip reconciliation of effective state. No internal JSON round trip is needed.

  • A combined tracker/priority edit remains one durable commit. This does not claim simultaneous effective application or rollback: file priorities may complete asynchronously.
  • An absent tracker edit differs from an explicitly empty tracker list.
  • Keep operation-specific legality explicit. Merge currently queues directly; Edit uses Act, which rejects moving torrents. Sharing code must not silently change that behavior.
  • Changes retains ordering and Store retains I/O. The shared routine does not become another transaction queue or persistence authority.

Delete: duplicated commit-before-apply choreography for these two edits, including duplicate tracker application decisions. A method that merely forwards replace_trackers is too shallow. A generalized patch/transaction framework is too broad.

Payoff: locality for accepted-versus-effective edit behavior; leverage across merge and explicit edits; one existing command interface remains the verification seam.

Implementation shape

Finish one understandable slice at a time

  1. Dialog lifetime and recovery. Establish one complete interaction; migrate all ordinary dialogs and their close/theme/deferred-Add callers together. Verify Add and one other draft editor survive cancelled or unsuccessful close.
  2. Accepted selection. Move the decision to the presentation owner, remove the window copy, and update direct callers. Verify declined discard retains the intended selection and draft; reconcile target removal while a prompt is open.
  3. Committed edits. Consolidate after operation-specific preparation. Verify replacement, clearing, merge/restart, combined priorities and failed persistence through existing checks.
  4. History. Move state and its algorithm together with no dependency on the whole engine. Preserve the externally visible series and its session behavior.

Verification should match the risk. Reuse the existing magnet Exit/Keep-input journey, tracker-draft reconnect journey, CommittedFiles checks and merge/restart coverage. Extend only a missing scenario that can lose input, select the wrong target or misreport a durable change. Do not add tests for private helper shape, class count, property forwarding or static text.

Compilation and relevant behavior checks belong to implementation. The transfer checks and desktop launches still follow the repository’s explicit-launch rules. This review ran neither builds nor tests, and it makes no runtime-success claim.

Acceptance rule: the final diff must remove the old coordination paths in the same slice. A new owner beside the old one is incomplete. A small extra type is acceptable when the full action becomes easier to read; a lower line count is useful evidence, not the objective.

When implementation changes ownership, update the narrow source map or contract statement that describes it. Keep this review as reasoning, not a second permanent rulebook.

Report 1 / Independent architectPerspective: ownership and coordination

Concentrate the decisions that change together

The original shortlist finds real duplication, but treats current ownership too much like a constraint. Existing ownership should be the starting hypothesis.

1. Dialog lifetime is the strongest change

MainWindow represents one-modal-dialog behavior through several references, completion sources, close flags and repeated lists. The duplication is an invariant represented in several places, not merely repeated lines. Put the native dialog, the task representing its complete interaction and its resumption behavior together in one private window-owned lifetime.

Do not finish that lifetime at ShowAsync if command submission or cleanup still remains. ConfirmRemove currently waits for RemoveTorrents before signaling completion. Suspending for Exit must also differ from ordinary cancellation. Keep content construction, validation, resizing and localization specific to each form.

A private type is justified if it binds these facts together. A public dialog interface, registry, queue or hierarchy is not. Restore the retained interaction rather than encoding resumption as ShowFiles with an empty target list and initialize=false. Reusing a native dialog versus recreating its view needs implementation validation; that choice must not leak into CloseWindow.

Deletion target: per-dialog completion fields, close-time enumeration, restoration flags, repeated deferred Add decisions and common-theme enumeration. Existing Exit-with-magnet-input coverage plus one additional draft-bearing editor and deferred Add scenario can verify the changed lifetime.

2. Consolidate prepared edits, not a replace_trackers call

MergeTrackers and Edit both prepare saved facts, persist them, assign them, update libtorrent and mark resume state unsaved. A generic save-and-callback helper already exists in Changes; adding another would gain little. The useful shared implementation applies one torrent’s prepared intended edit while already in ordered execution.

Merge prepares tracker replacement from current trackers and incoming URLs. Explicit Edit validates submitted fields. Both should reach the same commit/apply decision without an internal JSON round trip. A small edit value is worthwhile if it expresses absent versus explicitly empty tracker choices and optional priorities.

Preserve one durable commit for compound tracker/priority edits, delayed priority completion, and application when saved values already match but effective state still needs reconciliation. Do not route merge through Act just for reuse: Act currently rejects moving torrents. Legality is a product decision.

3. Reopen selection ownership

The table has actual selection, the window keeps accepted selection for rollback, the view model stores selection and retargets the inspector, and the inspector can refuse. Some distinctions are necessary, but the transition is not readable at one point. “The normal gesture is guarded” does not justify preserving the arrangement.

One presentation decision should accept or refuse the proposed selection and its inspector consequence. Native prompts and control focus remain in the window; the inspector retains its draft. Programmatic reveal, filtering and membership reconciliation must respect the same decisions. A generic navigation guard or shared IDraft interface would overgeneralize.

4. Source-file separation is not encapsulation

Engine::State methods all see the same state despite separate source files. Speed history is a credible extraction: its buffers, minute accumulator and counter belong with the retention/averaging algorithm. Supply samples; do not pass Engine::State, callbacks or a provider interface into the history owner.

The same argument does not yet justify extracting file-operation, checkpoint, addition and shutdown managers: those operations coordinate common membership and persistence. Settings declaration movement alone offers less benefit.

5. Keep the useful existing separations

Changes orders saved-document decisions; Store performs blocking work and delivers completions. Keep them. PipeClient already supplies command precedence and read coalescing; retain complete snapshots and visible detail reads. Typed values should replace repeated decoding or clarify an actual decision, rather than mirror every payload.

Suggested order: dialog lifetime, prepared edits, selection transitions, then history. Judge each by removed coordination and a shorter path from user action to its owner.

Report 2 / Independent architectPerspective: correctness and abstraction cost

Simplify the operation, not merely its layout

Fewer places should decide each operation. Similar code should remain separate when its behavior differs; scattered ownership should be fixed even when the ordinary path works.

1. Own full dialog completion and failed-close recovery

The proposed dialog consolidation is sound but incomplete if it only wraps ShowAsync. Close needs to wait for required cleanup: detachment, unsubscription, draft handling and modal ownership release. Otherwise the new helper permits a prompt while the old caller is still retiring.

A small private lifetime record can bind the native dialog, completion and resumption. Two straightforward calls in a specialized form are acceptable; removing every repeated line is not the goal. Avoid a modal queue, registry, common draft interface or configurable priority rules.

There is also a specific source-supported recovery gap. CloseWindow restores an editor only when keepDraft becomes true; that happens after awaiting CancelClose. Failure before that point or in another close-preparation step can keep the window alive after hiding the editor. Capture the presentation and restore still-valid unfinished input whenever close is abandoned. This is source reasoning, not a reproduced runtime defect.

2. Give accepted selection one product owner

Workspace.cs decides whether selection may discard a draft and keeps rollback selection. MainViewModel.Select assigns selection before independently deciding inspector targeting. Inspector again refuses target changes or close. CloseInspector also discards the boolean close outcome. One transition is spread across three promises.

Let MainViewModel own accepted product selection and its consequences. The window collects gestures, shows the native prompt and reflects accepted selection back into TableView. Inspector owns draft and detail context; meaningful refusal outcomes must be consumed. Recheck membership after a prompt.

Do not collapse inspector target and selected rows into one value. A hidden inspector can retain a draft, and a removed target may remain visible as unavailable. TableView should retain its own control mechanics. Remove the window’s duplicate accepted product selection, not all state that happens to refer to a torrent.

3. Share committed edits without changing their transaction

Merge and explicit Edit can share normalized intended fields and an internal commit/apply implementation. The outer paths retain preview/duplicate resolution, input validation and operation-specific legality. Call the common owner inside ordered execution.

Calling Edit by constructing JSON adds conversion and silently imports Act’s moving-torrent refusal. Separating tracker and priority commits weakens the compound edit. Priorities may complete later, so the shared routine must preserve the retained reply. No tracker repository, second queue or generic transaction module is justified.

Absent tracker choices, explicit empty lists, unchanged fields and saved-versus-effective differences all carry real meaning. A small concrete edit value may express these clearly; a second torrent model would not.

4. Extract only cohesive engine state

Partial implementation files are organization, not encapsulation. Speed history has a clear case because its two buffers and partial-minute accumulation are used together by one algorithm. Let it accept samples and provide a range; keep cadence and session identity in the engine.

Wholesale extraction into managers that each borrow State would replace direct code with a dependency web. Keep shared membership and operation coordination together until a candidate has useful inputs and outputs of its own.

5. Preserve separations with different jobs

Changes serializes durable document changes; Store handles blocking execution and completion delivery. The three Store instances isolate durable work, payload operations and potentially slow preview reads; they are not duplicate persistence authorities.

Summary, preview and inspector polling have different consumers and invalidation. Read/Withdraw already shares the useful scheduling rule. Keep concrete loops. For payloads, choose neither “type everything” nor “JSON forever”: decode into an existing value when it removes repeated knowledge.

Suggested order: dialog lifetime/recovery, accepted selection, committed edits; consider history independently. Reuse relevant behavioral checks, subject to launch and transfer restrictions. Success means fewer facts to synchronize and an action readable without reconstructing several owners’ promises.

Report 3 / Review against your prioritiesApplied by the primary reviewer after both architect reports

Spend code only where it reduces what I must understand

This is my application of your stated goal, not a claim that you personally authored or approved each design choice.

1. Readability is enough reason to change structure

The initial report demanded too much proof of a user-visible failure before considering some refactors. That confuses the reason to add a regression test with the reason to improve ownership. If accepting a selection requires reading the window, view model and inspector together, clearer ownership is a sufficient benefit.

Likewise, separate .cpp files are useful navigation but cannot protect a coherent piece of state. I would accept the small history owner because it moves necessary state and behavior together. I would reject a file-count-driven engine breakup because it makes direct relationships harder to follow.

2. Prefer an obvious operation to a configurable mechanism

Both architects’ dialog proposal earns its place if it removes the lists and close flags. It loses that benefit if it becomes a miniature dialog framework. A single active lifetime is enough. Specific Add, Files and Limits code should still show what happens when the person submits or cancels.

Selection deserves one accepted-state decision, not an event bus or navigation package. Prompt handling can remain explicit. The product has a handful of concrete journeys; it does not need an extensibility system for hypothetical screens.

3. Do not mistake similar statements for the whole shared operation

The committed-edit proposal should replace duplicate save/apply reasoning, rather than hide a single libtorrent call. But “one implementation” does not mean merge and explicit edit lose their distinct preparation or legality. A combined edit must remain one saved change, and its effective completion must remain truthful.

I would reject a design with callback hooks and flags for every phase. One small concrete intended edit is easier to read when it directly says which fields change. Both old paths must actually use the new owner; keeping a parallel implementation would defeat the task.

4. Apply the same judgment to work already underway

The schedule changes should not be excluded from architectural reasoning simply because they are uncommitted. The inspected changes have a useful direction: CreatePeriod and Reschedule use PeriodDraft.SetSpan for a coherent time edit, and the displayed draft label belongs to the draft. PeriodSpan remains the place for span arithmetic, while Week owns pointer capture and rendering.

Keep those responsibilities direct. Do not add another schedule coordinator or mirror the draft in a control-owned model. The lighter SetSpan notification path differs from ordinary field edits; keep that distinction tied to the actual live-drag need, and verify the other consumers still receive the state they need. This review has not measured rendering performance or certified the evolving schedule changes.

Local reuse of visual elements can serve a real frequent-update path. It should stay local to Week; a generic pooling framework would add machinery. Conversely, do not delete useful reuse just to reduce line count without checking the interaction it protects.

5. Keep what earns its complexity, and keep the plan finite

The native engine, on-demand WinUI process, ordered Changes and asynchronous Store have concrete jobs. Their age or current location is irrelevant; the responsibilities are the reason to retain them. The same applies to concrete pipe scheduling and stable display rows.

Selective typed values remain available when they reduce repeated interpretation. There is no need to convert every payload before fixing dialogs or selection. Global refresh optimization, wholesale engine decomposition and generalized polling should not become prerequisites.

My resulting priority: fix dialog lifetime and recovery first, then accepted selection, then committed edits. Finish with the small history extraction as an independent change. Keep each slice complete, delete superseded paths, and judge the whole diff by reading the common action from start to finish.

Practical acceptance question: after this change, can an experienced developer find the decision, follow the operation and understand completion without maintaining a mental list of other owners that must agree? If not, more named types or shorter functions have not solved the problem.

Final selection after all three reviews

Choose smaller obligations at each call site

The architects agree on the substantive changes. Their sequencing differs; the consolidated order keeps the two related UI slices together, then addresses the native edit transaction. History is independent and must not grow into a broader engine rewrite.

The four changes have concrete deletion targets. The deferred decisions have concrete reasons. That is the architecture to pursue: direct product owners with less coordination exposed to their callers.
